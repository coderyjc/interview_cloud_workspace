1设计目标与核心取舍

围绕「真实 Agent CLI + 浏览器多会话工作台」这个闭环，做了几个关键取舍：

进程模型：每条消息起一个 CLI 进程

不用长驻 SDK 会话，而是每次用户消息 spawn 一个 claude -p 单轮进程，随后用 --resume 续接。崩溃只影响单轮，并发天然成立，重启不残留。

数据职责分离

SQLite 是前端 transcript 的唯一真源（带单调 seq）；Claude 自己的会话存储只负责模型侧上下文，用于 --resume。二者解耦。

协议适配层

考试端点只说 OpenAI 协议，Claude Code 只说 Anthropic 协议。容器内起 LiteLLM 做双向翻译（含工具调用与流式）。

全自动执行

单用户本地场景，用 --dangerously-skip-permissions 让助手自由读写工作目录、跑命令。任务可取消、超时兜底。

2总体架构

全部组件运行在同一个 Docker 容器内；容器内同时部署了我们的 FastAPI 服务、真实的 claude CLI 和协议转换代理。

4关键机制

流式、断线重连与取消

  • 每个会话一条 WebSocket。CLI 的 stream-json 被解析为归一化事件：delta（文本分片）、tool/tool_update（工具状态）、result、error。
  • 事件先落库（带 seq）再广播；客户端连上后发 subscribe{after_seq}，服务端回放缺口并继续推实时事件，并用 seq 去重。
  • 取消：后端向 CLI 进程发 SIGTERM，避免僵死；全局并加上限与单轮超时兜底。

多会话与持久化

  • 每个会话独立工作目录 workspaces/<sid>/，上传材料与助手产出同目录，文件面板直接读该目录。
  • 会话元数据与消息在 app.db；关页、重启容器后历史仍在，继续发消息以 --resume 续接上下文。

协议适配（为什么需要 LiteLLM）

实测考试端点仅支持 OpenAI 协议：POST …/v1/chat/completions 返回 200，而 Anthropic 的 POST …/v1/messages 返回 404「此接口未开放」。 因此容器启动时用 EXAM_* 生成 LiteLLM 配置，把 Claude Code 的 Anthropic 请求（含 tool_use 与 SSE 流）翻译为 OpenAI 协议。

人工确认（Human-in-the-loop）

  • 通过 Claude Code 的 PreToolUse 钩子，在 Write / Edit / MultiEdit / NotebookEdit 执行前阻塞。
  • 钩子回调后端 /internal/approval；后端读取当前文件与修改后内容，计算统一 diff（新增/删除行）。
  • WebSocket 推送 permission_request，浏览器复用模态框展示 diff，提供「允许 / 拒绝 / 本次会话都允许」。
  • 允许→钩子退出码 0 放行；拒绝→退出码 2 阻断并把原因回传给模型；「本次会话都允许」在后端标记该会话自动放行。

  • 以非 root 的 node 用户运行（--dangerously-skip-permissions 拒绝 root）。
  • 凭据只经环境变量注入，.env 不入库；docker-compose.yml 通过变量插值读取。
  • 数据放在命名卷，会话/文件/CLI 会话存储在重启后保留。

7已知限制

  • 单用户、无鉴权，仅建议本地或受信网络使用。
  • 全自动执行有安全风险（助手可读写工作目录、执行命令）。
  • 协议转换层会引入少量延迟，少数边缘字段可能不完全保真。
  • 续聊依赖 Claude 会话存储；若清除，历史仍在但上下文会断。
